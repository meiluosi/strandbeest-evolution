# 平台设计：从设计器到 3D 打印的全链路

> 状态：设计稿（2026-10）。这是后续推进的依据；实现细节在各阶段开始时再细化。
> 英文版待补。

## 1. 愿景

做一个开源的 **Strandbeest 设计与验证平台**：

> 在浏览器里设计一只风力动力兽 → 用保真仿真评估它在各种场景下的表现 → 检查可打印性并导出 3D 打印文件 → 做出实体、测量 → 用实测数据校准仿真 → 带着更可信的仿真回到设计。

三个原则：

1. **仿真要能被实物反驳。** 没有实测校准的仿真只是假设。平台把"测量 → 校准"做成一等公民，而不是事后补的。
2. **一份设计，多处使用。** 同一份设计文档同时驱动运动学、演化、仿真、制造导出和界面，不允许各处各存一套参数。
3. **保真度可选，不可偷换。** 快速的简化模型用来交互和筛选，高保真仿真用来评估，二者用同一份输入、可以互相对照；每个结论标明来自哪一层。

## 2. 用户与场景

| 用户 | 想做什么 | 平台给他的 |
|---|---|---|
| 学习者 / 科普读者 | 看懂腿为什么这样走 | 交互演示、文章 |
| 设计者（主要用户） | 调出一个能做出来、能走的设计 | 设计器、演化、仿真、打印导出 |
| 研究者 | 跑实验、比较设计、复现结果 | 场景文件、批量运行、数据与脚本 |
| 创客 | 照着做一只小的 | 打印文件、物料清单、装配说明、测试台方案 |
| 贡献者 | 加新地形、新驱动、新指标 | 注册表扩展点、契约测试 |

## 3. 核心概念与数据契约

平台的骨架是几份**带版本的、语言无关的数据文档**。它们是各组件之间唯一的接口。

| 文档 | 含义 | 谁生产 / 谁消费 |
|---|---|---|
| **Design** | 一只动力兽本身：连杆规格与长度、腿数与相位、机身、驱动（帆/电机/传动比）、材料与制造参数 | 设计器、演化产出；仿真、制造、界面消费 |
| **Scenario** | 一次仿真的环境与设置：地形、风、驱动模式、求解器、输出；引用某个 Design | 用户/界面编写；仿真消费 |
| **Run** | 一次仿真的结果：解析后的完整配置、时间序列、指标、代码版本、随机种子 | 仿真产出；界面、校准消费 |
| **Build** | 一个实体：对应哪个 Design 版本、用什么打印设置/材料、装配备注 | 用户填写 |
| **Measurement** | 实测数据：关联 Build 与测试条件，含扭矩、转速、风速、轨迹的时间序列 | 测试台产出；校准、对照消费 |
| **Profile**（校准结果） | 由实测拟合出的参数集（如 PLA 销轴摩擦、接触刚度、帆阻力系数），带出处 | 校准产出；Scenario 引用 |

关键规则：

- **JSON Schema 为唯一来源**（`schemas/`），放在仓库根目录，TypeScript 类型和 pydantic 模型由它生成，二者都用同一批示例文件做契约测试。这是因为核心是 TS、仿真是 Python，不能让任何一边成为"事实标准"。（目前 `packages/sim` 里的 pydantic 模型是临时的，P1 迁移。）
- **每个文档带 `schema_version`**，破坏性变更必须提供迁移函数。
- **Run 必须可复现**：保存解析后的完整配置、`git` 提交号、种子、库版本。
- **每个猜测的物理参数都是命名字段**，默认值标 `assumption`，并随 Run 一起保存。

## 4. 系统架构

```
                            ┌──────────────────────────── apps/web（Svelte） ───────────────────────────┐
                            │ 设计器 · 演化 · 场景编辑 · 结果查看 · 制造预览 · 实验室笔记 · 社区设计库     │
                            └───────────┬───────────────────────────────┬──────────────────────────────┘
                     浏览器内计算（快）    │                               │ HTTP / WebSocket（慢任务）
                  packages/core（TS）◄────┘                               ▼
          运动学 · 演化 · 简化动力学                          apps/api（Python FastAPI）
                                                    设计/场景/运行/导出/测量/校准 的 REST + 任务队列 + 进度推送
                                                              │            │             │
                                              packages/sim（MuJoCo）  packages/fab   packages/calib
                                              场景化高保真仿真         可打印几何导出   参数拟合
                                                              │            │             │
                                                              └─────── 存储（SQLite/Postgres + 文件/对象存储）
                                                                   designs · scenarios · runs · builds · measurements · profiles

  线下：hardware/（测试台方案、固件、数据采集脚本）──► 产出 Measurement 文件 ──► 上传到 api 或放进仓库
```

### 4.1 组件职责

- **`schemas/`**：JSON Schema + 示例 + 迁移函数。无运行时代码。
- **`packages/core`（TypeScript，已有）**：运动学求解、步态指标、遗传算法、简化动力学。纯逻辑、可在浏览器运行，是设计器的"实时反馈层"。
- **`packages/sim`（Python + MuJoCo，已有 S1）**：从 Design + Scenario 生成模型并运行。地形、风、驱动、指标走注册表。可作为库、命令行或被 api 调用。
- **`packages/fab`（Python，新增）**：从 Design 生成可打印零件。拟用 CadQuery 做参数化建模，输出 STL/3MF/STEP，以及可选的激光切割 SVG/DXF；做可打印性检查（最小壁厚、销轴间隙、热床尺寸、打印朝向）；生成物料清单和装配说明。
- **`packages/calib`（Python，新增）**：读取 Measurement 与对应 Scenario，用优化器（如 CMA-ES）拟合 Profile，并报告拟合残差与不确定度。
- **`apps/api`（Python FastAPI，新增）**：薄的编排层。耗时任务（仿真、批量、导出、校准）入队列，状态与进度通过 WebSocket 推给前端。不含物理逻辑。
- **`apps/web`（Svelte，由现有 `web-demo` 演进）**：见 5。
- **`hardware/`（新增）**：测试台说明与物料、微控制器固件（扭矩/电流、编码器、风速计）、视频追踪脚本；产出符合 Measurement 契约的文件。

### 4.2 API 草图（P4 细化）

```
POST   /designs            GET /designs/{id}      PUT /designs/{id}
POST   /scenarios          GET /scenarios/{id}
POST   /runs               {design_id, scenario_id | inline scenario}  → job
GET    /runs/{id}          状态 + 指标；  GET /runs/{id}/series  时间序列（分块）
POST   /sweeps             参数扫描 → 一组 runs
POST   /exports            {design_id, format, options} → job → 文件
POST   /measurements       上传实测；  POST /calibrations  {profile_target, measurement_ids} → job
WS     /jobs/{id}/events   进度与日志
```

任务队列起步用进程内 worker 池 + SQLite（单机够用），需要时换 Redis/RQ 或基于 Postgres 的队列；存储走一个抽象接口（本地文件 → 以后可换对象存储）。

### 4.3 部署形态（一套代码，三种模式）

| 模式 | 组成 | 适用 |
|---|---|---|
| **静态** | 前端 + 预先算好的 Run/Design 文件，放 GitHub Pages | 科普与成果展示，零运维 |
| **本地** | `docker compose`：web + api + worker | 设计者自己用，数据在本机 |
| **托管** | 同上放到云上，加登录、配额、限流 | 对外开放；成本与滥用风险最高，放最后 |

浏览器内运行 MuJoCo（WebAssembly）是"托管"之外的另一条路：不需要后端算力，但性能和稳定性要实测后再定。

## 5. 前端功能分区

1. **设计器**：拖动长度看脚轨迹（已有），腿数/相位、机身、驱动参数；一键演化（已有，浏览器内）；设计保存为 Design 文件。
2. **仿真**：场景表单直接由 Schema 生成；提交、看进度；结果查看器（机体动画、扭矩与速度曲线、接触与打滑诊断），多次运行并排对比。
3. **制造**：零件三维预览、可打印性报告（哪里太薄、间隙够不够、超不超热床）、下载 STL/3MF、物料清单、装配步骤。
4. **实验室**：登记 Build，上传 Measurement，把实测曲线叠在仿真曲线上，查看校准前后的差距。
5. **设计库**：社区设计以文件形式放在仓库里，通过 PR 贡献，前端读取展示。起步不需要账户系统。

## 6. 关键链路细节

### 6.1 保真仿真到 3D 打印

这是整个平台最容易被低估的一段。仿真里的"理想销轴"在打印件上是**有间隙、有摩擦、会磨损的塑料轴孔**。因此：

- Design 中的"制造参数"（销轴直径、配合间隙、杆件截面、材料、打印层高）必须进入仿真：**关节摩擦、间隙和杆件柔度是仿真的可配置效应**，而不是制造时才考虑的事。
- `fab` 的输出要保证几何与仿真一致：同一份 Design 生成零件，孔位精度由测试保证（几何单元测试：孔心距与设计一致到容差内）。
- MVP 阶段先让导出包完整可用；**线下打印后**，用打印件手摇检查脚轨迹是否与设计一致，结论回灌到间隙与摩擦的默认值。这一步不阻塞其他开发。

### 6.2 测量与校准

- 测试台两组实验：**电机驱动无风**（扭矩–角度曲线、步幅、打滑）校准接触与摩擦；**风扇加帆**（起步风速、速度–风速曲线）校准帆与风。
- 校准目标是少量**有物理意义的参数**，不是把所有东西拟合成黑箱。拟合后保留残差，残差大说明模型缺东西，而不是继续调参数。
- 校准结果写成 Profile，场景用名字引用，例如 `profile: pla-0.4mm-printed-pin`。

### 6.3 多保真度优化

演化循环不直接用高保真仿真（太慢）：

1. 简化模型（`core`）跑大规模遗传算法，筛出候选；
2. MuJoCo 仿真复评前若干名；
3. 对实测校准过的最好一两个设计做实体验证。

简化模型与高保真的偏差本身是被持续监控的量（见第 8 节）。

## 8. 质量与验证策略

- **契约测试**：同一批示例文档，TS 与 Python 双边校验；迁移函数有往返测试。
- **交叉验证**：简化模型 ↔ MuJoCo 的对照脚本（已有雏形）纳入 CI，设定"允许偏差"并在超出时失败，防止悄悄漂移。
- **回归**：仿真的关键指标（步幅、起步风速等）用金标文件加容差。
- **几何测试**：`fab` 输出的孔位、尺寸、间隙与设计一致。
- **诚实记录**：每个实验的结论、参数、局限写进 `docs/EXPERIMENTS.md`，包括否定性结果（现在已有先例）。
- **CI**：Node 与 Python 矩阵；仿真类慢测试用标记分开。

## 9. 阶段计划

### 9.1 MVP 定义：先走通全流程（walking skeleton）

MVP 不是"某一环做到最好"，而是**每一环都有一个能跑的最薄实现，端到端串起来**：

```
Design ─► 评估(简化) ─► 仿真(MuJoCo) ─► 可打印性检查 + 导出(STL/BOM/装配) ─► [线下打印、测量]
   ▲                                                                              │
   └──── 校准后的 Profile ◄── 校准 ◄── 与仿真对照 ◄── Measurement(上传/导入) ◄────────┘
```

- **线下打印与测量不是卡点。** 没有实测数据时，用**合成数据**（用已知参数的仿真加噪声生成）验证"导入 → 对照 → 校准"这条链路本身是对的；真实数据到了再替换。
- 每一环的退出标准是"契约 + 测试 + 一条命令能跑"，**不是**"物理上准确"。物理准确性由后续阶段逐环加深。
- 前后端同样先做最薄：一个 API 提供"校验设计 / 提交仿真 / 导出打印包"，前端能走完同一条路径。

### 9.2 阶段

| 阶段 | 目标 | 退出标准 | 主要负责 |
|---|---|---|---|
| **P0 基础**（已完成大半） | 核心库、网页演示、仿真 S1、文档 | 已有；仿真扭矩尚未收敛 | 已完成 |
| **MVP 走通全链路** | 契约（`schemas/`）、`fab` 导出、测量与校准（合成数据）、薄 API、前端走通；一条命令串起 | 从一份 Design 出发，一次命令得到：评估结果、仿真结果、可打印性报告、STL/BOM/装配说明；合成测量能被导入、对照并校准出已知参数 | 我 |
| **P1 可信的仿真** | 接触模型研究（刚度、摩擦、脚几何）、时间步长收敛 | 默认接触设置下扭矩对参数不再剧烈漂移，或明确记录"不可靠区间" | 我 |
| **P2 前端完整化** | 设计器、结果查看器、制造预览、实验室页面 | 不开后端也能浏览预先算好的结果；开后端能提交与对比 | 我（你可参与界面） |
| **P3 制造加深** | 整机框架/曲轴、销轴与间隙默认值、多种材料/工艺 | 你线下打印后，用结果回灌间隙与摩擦默认值（不阻塞其他阶段） | 我写，你打印 |
| **P4 后端加深** | 任务队列、存储、批量扫描、`docker compose` | 界面里提交场景、看进度、对比多次运行 | 我 / 你一起 |
| **P5 测试台与真实数据** | 测试台方案与固件、数据采集脚本、首批实测 | 一份完整的"电机驱动无风"数据集与仿真对照 | 你动手，我写工具 |
| **P6 校准与扩展仿真** | 真实数据校准；仿真 S2–S4（帆与风、杆件/关节效应、沙地）；多保真度演化 | 校准后的仿真在留出数据上的误差有定量结论 | 我 |
| **P7 对外发布** | 托管或浏览器内仿真、文档站、社区设计库、英文文档、成果报告 | 外部用户无需安装即可设计—仿真—导出一只小动力兽 | 共同 |

依赖：MVP 之后，P1/P2/P3/P4 大体可并行；P5 依赖 P3 的打印件；P6 依赖 P5。**P1 没做好之前，不要在仿真结果上做重的前端/后端投入**，MVP 里的前后端因此只做最薄。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| 仿真扭矩对接触参数过于敏感，无法预测真机 | P1 先量化敏感度；P5/P6 用实测校准；结论里明确适用范围 |
| 3D 打印销轴的间隙、摩擦、磨损决定成败 | P3 先打一条腿；把间隙与摩擦做成可配置效应并进入校准 |
| 小模型的比例效应使结论无法外推 | 小模型主要用于校准模型而非直接外推；论文式报告里写清楚 |
| 范围过大、单人维护 | 严格按阶段与退出标准推进；契约与测试先行；设计库走 PR 贡献 |
| 托管的算力成本与滥用 | 静态/本地模式优先；托管最后做，并加限流与配额 |
| 参数里的"假设"被当成事实 | 命名字段 + 默认值标注 + 随 Run 保存；文章与界面都显示来源 |
