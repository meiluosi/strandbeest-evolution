# 行动计划：任务卡

> 用法：**点名派活**，例如"做 E1-01"或"把 E3 整个做完"。每张卡有目标、验收（可验证的门槛）、依赖、规模和"需要你做什么"。
> 来源：[ENGINE.md](ENGINE.md)（架构迁移 E0–E8）、[VISION.md](VISION.md)（玻璃盒 G、AI 原生 A、算法 O、物理 S、制造 F）、[adr/](adr/)（已接受的决定）。
> 状态栏：⬜ 未开始 ▶ 进行中 ✅ 完成。 规模：**S** 约半天内、**M** 约一两天、**L** 多天或需要调研。

## 0. 通用约定

### 完成的定义（Definition of Done）
每张卡完成时必须同时满足：
1. `pnpm check`、`./scripts/test-python.sh`、`svelte-check` 全绿；新增行为有测试（不是只有"能跑"）。
2. **验收条件逐条有证据**（测试名、命令输出或数字），写在提交信息或 `docs/EXPERIMENTS.md` 里。
3. 触及 schema → 同时给**迁移函数和往返测试**；触及用户可见文字 → 走 i18n 消息键（E1 之后）。
4. 任何**数值结论**写进 `docs/EXPERIMENTS.md`，**含否定性结果**，并标明"模型内"还是"实测"。
5. 影响架构的改动同步更新对应 ADR（状态或"后果"小节）和本文件的状态栏。
6. 提交信息用 Conventional Commits；**不对外发布**（npm、Pages、博客、打印导出）除非任务卡明确写了并由你确认。

### 诚实规则（项目的底线）
猜测的物理参数必须有名字并标 `assumption`；没验证的写"未验证"；发现旧结果有误要**回头更正**并留痕；优化目标要附"防钻空子"压力测试。

### 优先级与依赖图（总览）
```
E0 约定 ─┬─► E1 i18n + 属性系统 ─┬─► E2 资产 ID ──┬─► E3 结构化设计 + 编辑代数 ─┬─► A 智能体
         │                       │               │                            └─► O 优化工具箱
         └─► E0-03 运动学语料库 ───┘               └─► E5 出处/缓存/作业 DAG ──► G 玻璃盒（实时部分）
                                  E4 世界/实体/后端 ─► E5, G, 兽群
                                  E6 数据格式 ───────► G（回放层）
   S 物理保真度、F 制造与真实世界、R 发布：基本独立，F/R 需要你参与
```

### 建议的波次
| 波次 | 内容 | 为什么这个顺序 |
|---|---|---|
| **Wave 1（地基）** | E0-01…E0-04 → E1-01、E1-03 → E2-01、E2-02 | 纯约定和机械迁移，越早越省；做完后所有新功能都建在新地基上 |
| **Wave 2（支点）** | E3-01…E3-04、E4-01…E4-03、E1-04 | 编辑代数 + 后端边界；之后 AI、优化、玻璃盒才有地方挂 |
| **Wave 3（看见过程）** | G-01…G-05、E4-05、E4-06、E6-01…E6-03、E5-01…E5-03 | 回应"要看到仿真的过程"；缓存让大量实验变便宜 |
| **Wave 4（智能）** | A-01…A-04、O-01…O-04 | 在稳定的操作与属性层上，agent 和优化器几乎是白拿 |
| **随时** | S、F、R、Q 各卡 | 独立，按你的兴趣和手头资源插入 |

## 如何给我派活

最省事的写法：
> "做 E0-02 和 E0-03。"
> "把 E2 整个做完，迁移前先给我看迁移计划。"
> "G-01 到 G-03，做完让我看效果。"

我会：先复述验收条件，**发现卡片与现状不符就先指出**（比如验收写得做不到、依赖没满足），再实现、测试、更新文档和状态栏，最后用数字汇报"验收是否逐条满足、哪些没满足"。涉及对外发布或需要你的硬件/账号的卡，我只做准备，不替你执行。
